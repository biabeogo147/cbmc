\section{Introduction}
\label{sec:introduction}

OSEK/VDX~\cite{lemieux_programming_osek_vdx_2001,osek_vdx_spec_223} is an automotive operating-system standard introduced in 1994 by European automobile manufacturers, suppliers, and the University of Karlsruhe. It was created to manage the increasing amount of software in vehicles while improving product quality and reliability. The standard has been adopted by major car manufacturers such as BMW, Opel, and Toyota, and is used to support vehicle applications such as cruise control and temperature control. Because these applications directly affect vehicle operation and driver safety, ensuring their reliability is essential. However, as automotive software becomes more complex, verifying the correctness and reliability of OSEK/VDX applications remains a significant challenge.

\subsection{OSEK/VDX Applications and Model Checking}

An application developed on OSEK/VDX OS consists of multiple tasks. To concurrently execute multiple tasks on one CPU, OSEK/VDX scheduler uses \textit{static priority scheduling policy} with non-preemptive strategy and full-preemptive strategy to determine the running task. In particular, Figure~\ref{fig:osek-scheduler} shows that a ready queue in scheduler is used to lay out the execution order of tasks. OSEK/VDX OS can process two types of tasks, basic task and extended task. The states of a basic task consist of \textit{running state}, \textit{ready state} and \textit{suspended state}. Compared with the basic task, the extended task can hold synchronization events and has a unique state called \textit{waiting state}.

OSEK/VDX OS also provides standardized application interfaces (APIs), such as \texttt{ActivateTask}, \texttt{TerminateTask}, \texttt{SetEvent}, and \texttt{WaitEvent}, through which tasks can dynamically change task states, synchronization events, and shared resources.

To ensure the reliability of OSEK/VDX applications, testing is an important checking technique used in industry, but it is difficult to exhaustively check OSEK/VDX applications using testing technique, especially because of incomplete test-cases. In addition, it is hard to reproduce an error trace when an error is detected by testing, due to the concurrency of OSEK/VDX applications.

Model checking~\cite{clarke_emerson_model_checking_2009,clarke_grumberg_long_model_checking_abstraction_1994}, an efficient and exhaustive verification technique for concurrent software, can be applied to verify OSEK/VDX applications instead of testing technique. Particularly, it will return a counterexample when detecting an error. Based on the returned counterexample, developers can easily find the error trace and reproduce the erroneous behaviours.

\subsection{Shortcomings of Existing Model Checking for OSEK/VDX Applications}

Existing model checking methods~\cite{holzmann_spin_model_checker_2003,andrews_qadeer_rajamani_rehof_xie_zing_2004,wachter_kroening_ouaknine_impact_2013}, such as the ANSI-C multi-threaded software and SystemC multi-threaded software, have been applied to verify
concurrent software. In these methods, the behaviours of scheduler are taken into account in the verification process.
However, these prominent model checking methods are still unsuitable to accurately verify OSEK/VDX applications because of different scheduling policy. As shown in Figure~\ref{fig:diff-schedulers}, in the existing methods, the running thread within the concurrent software is arbitrarily determined by scheduler (non-deterministic scheduler is used to dispatch threads), but in OSEK/VDX applications which task is to be run is explicitly determined by OSEK/VDX scheduler, a deterministic scheduler used to dispatch tasks.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.8\linewidth]{figures/diff-schedulers.png}
  \caption{The difference of schedulers}
  \label{fig:diff-schedulers}
\end{figure}

If such methods are applied directly to OSEK/VDX applications, the verification process becomes too imprecise because the behaviours of OSEK/VDX scheduler are not taken into account. As a result, a large number of unnecessary interleavings of tasks may be checked in the verification stage, which can lead to spurious bugs and increases the checking costs in terms of judging time and memory of checking devices. 

\subsection{Research Purpose \& Contribution}

The purpose of this report is to make model checking more accurate for OSEK/VDX applications. In order to achieve this purpose, we describe and develop an approach to construct a checking model that reflects their execution semantics and avoid checking ISR occurrences at program locations that do not affect the checking results.

In our approach, we introduce how the checking model is constructed before the final verification stage. During checking-model construction, a recognized OSEK/VDX API call is not treated only as an ordinary C function call. Instead, it updates the representation of the current execution state, including the running task, the ready queue, the waiting tasks, and the stored event state of each relevant task. After processing a recognized API call, the checking model updates the current scheduling state. From this updated state, the deterministic scheduler determines what is checked next: execution may remain in the current task, switch immediately to a ready task, return to the interrupted context that preceded the current task, or finish the current task and start another ready task. In addition, some recognized API calls write the stored event state back to program variables, so later branch conditions and assertions can depend on that state. As a result, the checking model is constructed from these state updates and the resulting dispatch decisions, rather than from the ordinary local control flow of the current task alone.

To avoid checking unnecessary interleavings, our approach also constructs a manifest, which is an intermediate description used in checking-model construction: for each ISR, the manifest records the shared or global state that the function can write, and the source locations where that function needs to be represented in the checking model. This manifest is built by identifying the ISR or interleaving functions under consideration, summarizing the shared or global state that each of them can modify, and then scanning the remaining program to find the program points where reads, writes, branch conditions, or scheduling effects can be changed by that state. The final checking model then introduces guarded ISR behaviour only at the source locations recorded in the manifest, so that the verification still reflects the task execution order determined by the deterministic scheduler while avoiding unnecessary interleavings and reducing spurious bugs.

The report makes three contributions:

\begin{itemize}[leftmargin=1.5em]
\item It describes a checking approach for OSEK/VDX applications whose task execution order is determined by a deterministic scheduler, task states, synchronization events, and a ready queue.

\item It introduces a manifest-guided method for selecting ISR insertion locations and building a checking model with ISR calls only at the program locations recorded in the manifest.

\item It presents benchmark results showing that the proposed approach reduces unnecessary interleavings and removes spurious bugs reported by the baseline checking process.
\end{itemize}
