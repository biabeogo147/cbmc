\section{Methodology}
\label{sec:method}

\subsection{Overview of the Proposed Approach}

The proposed approach builds on the baseline CBMC architecture described in \Cref{sec:background} and summarized in \Cref{fig:baseline-cbmc}. It does not replace bounded model checking, symbolic execution, or the solver backend. Instead, it changes how the checking model is constructed before final verification. The goal is to make the model more accurate for OSEK/VDX applications, where task execution order is determined by the deterministic scheduler, the ready queue, task states, and the APIs invoked from tasks.

The approach has two main parts. The first part is handling OSEK/VDX scheduler behaviours. During verification, the checking model must represent how OSEK/VDX APIs change task states, synchronization events, shared resources, and the ready queue. This allows the next running task to follow the behaviours of the OSEK/VDX scheduler rather than ordinary C control flow alone.

In terms of the first part, during verification, the checking model must represent how OSEK/VDX APIs change task states, synchronization events, shared resources, and the ready queue. This allows the next running task to follow the behaviours of the OSEK/VDX scheduler rather than ordinary C control flow alone.

The second part is manifest-guided interrupt service routine (ISR) insertion. In this report, an ISR is a function that may interrupt the normal execution of tasks. A naive model may insert ISR calls at many program locations by using \texttt{\_\_CPROVER\_ASYNC\_X}, which can create unnecessary interleavings and increase the checking cost. To avoid this, the proposed approach first computes a manifest, which records the selected program locations where ISR calls should be inserted. The source tree is then rewritten according to this manifest, producing a new checking model for CBMC.

The key point is that the proposed approach keeps CBMC as the bounded model checker, but changes the model that CBMC receives. Instead of verifying a model that treats scheduling and interrupt effects too broadly, the approach constructs a checking model that better reflects the executions of OSEK/VDX applications.

The remainder of this section explains the approach in three steps. \Cref{sec} describes how OSEK/VDX scheduler behaviours and APIs invoked from tasks are represented. \Cref{sec} explains how the manifest is used to reduce unnecessary ISR insertion points. \Cref{sec} explains how the checking model that takes the OSEK/VDX scheduler into account and the manifest-guided insertion step are combined before CBMC performs final verification.

To keep the discussion concrete, the remainder of this section uses one synthetic running example. \textit{Task1} is a higher-priority extended task that waits for an event.\textit{Task2} is a lower-priority task that can run while \textit{Task1} is in waiting state. \textit{ISR1} updates shared state and sets the event awaited by \textit{Task1}. The example is intentionally small, but it is large enough to show the three main decisions in the methodology: how task execution order is determined, how unnecessary interleavings are reduced, and how the final checking model is built.

\subsection{Taking the OSEK/VDX Scheduler into Account}

The first methodological step is to represent the behaviour of the OSEK/VDX scheduler inside the checking model. In an OSEK/VDX application, the next running task is not chosen by an unstructured interleaving of threads. It is chosen by a deterministic scheduler that depends on task states, priorities, events, and the ready queue. If the checking model ignores those elements, the resulting task execution order no longer matches the execution order of the application.

Listing~\ref{lst:running-example} shows the running example used throughout this section. The example combines waiting, event signaling, shared-state update, and an local computation so that each later step can be explained with reference to the same program.

\begin{lstlisting}[language=C,caption={Pseudo Code},label={lst:running-example}]
int shared_ready = 0;
int shared_value = 0;

TASK(Task1)
{
    EventMaskType observed = 0;
    WaitEvent(EVENT_SHARED_READY);
    GetEvent(TASK_1_ID, &observed);
    if ((observed & EVENT_SHARED_READY) != 0u && shared_ready) {
        int sample = shared_value;
        assert(sample >= 0);
    }
    ClearEvent(EVENT_SHARED_READY);
    TerminateTask();
}

TASK(Task2)
{
    int checksum = 0;
    checksum = checksum + 1;
    checksum = checksum * 2;
    TerminateTask();
}

ISR(ISR1)
{
    shared_value = 7;
    shared_ready = 1;
    SetEvent(TASK_1_ID, EVENT_SHARED_READY);
}
\end{lstlisting}

The central point is that the standardized APIs in Listing~\ref{lst:running-example} cannot be treated as ordinary function effects. When \textit{Task1} executes \texttt{WaitEvent}, the important effect is not only that a C function is called. The important effect is that \textit{Task1} may move from running state to waiting state. Once this happens, the scheduler may select textit{Task2} as the next running task because \textit{Task2} is already in ready state.

Later, when \textit{ISR1} executes \texttt{SetEvent}, the event state changes and
\textit{Task1} may move from waiting state back to ready state. Because \textit{Task1} has higher priority than \textit{Task2}, the deterministic scheduler may dispatch \textit{Task1} before \textit{Task2} continues. Therefore, the checking model must represent changes to task states, events, and the ready queue, not only ordinary control-flow changes inside the current C function.

Therefore, the checking model must represent this cycle explicitly instead of treating API calls as ordinary function calls.

Read clockwise, some OSEK/VDX APIs change task states or event state. For example, \texttt{WaitEvent} may move an extended task from running state to waiting state when the awaited event is not set, while \texttt{SetEvent} may make a waiting task ready again by setting the awaited event. Other APIs, such as \texttt{GetEvent}, read event information that is already stored in the checking model. After each relevant API action, the checking model updates the task states, the event state, and the ready queue. The deterministic scheduler then uses this information to determine the next running task. That task execution order determines the next checking step, which may later reach another API call or another state update.

In the running example, this means that the verification path should not simply continue with the next statement in the C code after \texttt{WaitEvent} when the awaited event is clear. Instead, the checking model should represent that \textit{Task1} moves to waiting state, that \textit{Task2} may run while \textit{Task1} is waiting, and that \textit{ISR1} can set the event and make \textit{Task1} ready again. In this way, the task execution order in the verification result can reflect the execution order determined by the OSEK/VDX scheduler.

\subsection{Reducing Unnecessary Interleavings}

After the checking model represents the OSEK/VDX scheduler, the next step is to control where interrupt service routine (ISR) calls are inserted. If ISR calls are inserted at too many program locations, the checking model may include many interleavings that do not affect the property being checked. These unnecessary interleavings can increase the checking costs in terms of states, time, and memory, and may also lead to spurious bugs.

Therefore, the proposed approach first identifies the program locations where ISR calls are relevant to the checked execution. These selected locations are recorded in a manifest. The later rewriting step uses this manifest to insert ISR calls only at those selected locations, instead of adding them broadly across the program.

The key question is therefore not ``where could an ISR call be inserted in general?'', The key question is ``where can an ISR call change the checking result?''. In the running example, \textit{ISR1} is relevant when its updates to \texttt{shared\_ready} and \texttt{shared\_value}, or its call to \texttt{SetEvent}, can be observed later by \textit{Task1} or by the scheduler.

If inserting \textit{ISR1} at a program location cannot change a task state, event state, ready queue, or assertion result, then that insertion only adds an unnecessary interleaving to the checking model.

In the running example, \textit{ISR1} has three visible effects: it writes \texttt{shared\_value}, sets \texttt{shared\_ready}, and calls \texttt{SetEvent(TASK\_1\_ID, EVENT\_SHARED\_READY)}. These effects matter when they can be used later by \textit{Task1} or by the scheduler. For example, the call to \texttt{SetEvent} can move \textit{Task1} from waiting state back to ready state, and the writes to \texttt{shared\_ready} and \texttt{shared\_value} can affect the later \texttt{if} statement and assertion in \textit{Task1}.

By contrast, the checksum statements in \textit{Task2} only update the local variable \texttt{checksum}. They do not read \texttt{shared\_ready} or \texttt{shared\_value}, they do not inspect the event state, and they do not invoke an OSEK/VDX API that changes task states or the ready queue. Therefore, these local statements do not create additional points.

The point of Table~\ref{tab:selected-points} is not to predict exactly when \textit{ISR1} will occur. The point is to decide where inserting an \textit{ISR1} call is useful for the checking model. The selected locations are the places where \textit{ISR1} can change what \textit{Task1} or the scheduler observes, such as the event state, \texttt{shared\_ready}, \texttt{shared\_value}, or the next running task.

The skipped locations are different. In this example, the checksum statements in
\textit{Task2} only update the local variable \texttt{checksum}. They do not read the event state, they do not read \texttt{shared\_ready} or \texttt{shared\_value}, and they do not change task states or the ready queue. Skipping separate ISR insertions at those locations therefore reduces unnecessary interleavings without removing behaviour that can affect the checked path.

\subsection{Building the Final Checking Model}

The proposed approach combines the previous two steps to build the final checking model. First, it selects the program locations where an \textit{ISR1} call can change what \textit{Task1} or the scheduler observes. These locations are recorded in the manifest. Second, it uses the manifest to build a checking model in which ISR calls appear only at the selected locations.

This separation makes the method easier to control. The selection step answers the question: ``where can an ISR call affect the event state, the ready queue, the shared variables, or the assertion checked by CBMC?'' The model-building step answers a different question: how should the final checking model represent only those selected ISR calls?

As a result, the final checking model does not insert ISR calls at every possible program location. It keeps the locations that can affect the checked path and skips locations that only add unnecessary interleavings. This reduces the checking cost while preserving the behaviours needed for the running example.

For the running example, the selected locations can also be summarized in the compact form
shown in Listing~\ref{lst:selected-summary}. This summary connects the selection step with
the model-building step: it records where \textit{ISR1} should be inserted, without showing
low-level implementation details.

\begin{lstlisting}[caption={Readable summary of the selected ISR insertion locations for the running example.},label={lst:selected-summary}]
Selected ISR insertion locations:
1. Before WaitEvent(EVENT_SHARED_READY)
2. Before GetEvent(TASK_1_ID, &observed)
3. Before the if statement that checks observed and shared_ready
4. Before the read of shared_value

Skipped locations: The local checksum updates inside Task2
\end{lstlisting}

Conceptually, the upper lane starts from the original program and proceeds directly to model
construction, symbolic execution, and bounded model checking. The lower lane inserts four
additional responsibilities. The first added block builds a project-scoped view of the
program rather than a single straight-line execution view. The second added block identifies
where interruption-written state can affect the checked path. The third added block rebuilds
a restricted source-level checking model that retains interruption-related behaviour only at
those selected points. The fourth added block applies scheduler-consistent symbolic execution
so that standardized APIs change task states, the ready queue, and task execution order in a
way that matches OSEK/VDX semantics. This is the second major difference from baseline CBMC:
the proposed approach changes both where interruption-related behaviour appears and how the
resulting task execution order is interpreted during verification.

Listing~\ref{lst:restricted-checking-model} shows the output of the constructive step for the
running example. The guarded calls are part of the checking model, not part of the original
application program. They are placed only at the selected points. No such call is inserted
inside the local checksum updates of \textit{Task2}, because those updates were excluded
as unnecessary interleavings in Table~\ref{tab:selected-points}.

\begin{lstlisting}[language=C,caption={Illustrative restricted checking model for the running example.},label={lst:restricted-checking-model}]
TASK(Task1)
{
  EventMaskType observed = 0;
  if (nondet_bool()) ISR_Sensor(0);
  WaitEvent(EVENT_SENSOR_READY);
  if (nondet_bool()) ISR_Sensor(0);
  GetEvent(TASK_ID_Control, &observed);
  if (nondet_bool()) ISR_Sensor(0);
  if ((observed & EVENT_SENSOR_READY) != 0u && sensor_ready) {
    if (nondet_bool()) ISR_Sensor(0);
    int sample = sensor_value;
    assert(sample >= 0);
  }
  ClearEvent(EVENT_SENSOR_READY);
  TerminateTask();
}

TASK(Task2)
{
  int checksum = 0;
  checksum = checksum + 1;
  checksum = checksum * 2;
  TerminateTask();
}
\end{lstlisting}

The methodological role of Listing~\ref{lst:restricted-checking-model} is straightforward.
The checking model still admits interruption-related behaviour, but only at points where that
behaviour can change the execution being checked. This preserves the main advantage claimed
in Sections~1 and~2: fewer unnecessary interleavings without ignoring the OSEK/VDX
scheduler or the shared state written by interruptions.
